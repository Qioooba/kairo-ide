# Progress — v0.3-jdt-ls-skeleton

> Tag: `v0.3-jdt-ls-skeleton`
> Round: P2 (Java editing) — phase 1 of 2
> Date: 2026-07-18

This is the **first half** of P2. It does NOT yet give you Java
language features in the editor. What it gives you is the
honest plumbing that the user explicitly called out as a
prerequisite: the fake `setState('ready')` is gone, the JDT LS
state is the wire truth, and the agent refuses to lie about
"ready" until the LSP `initialize` handshake has actually
completed. The second half — wiring the LSP frame stream to
Monaco so the editor actually does completion, hover, goto, etc.
— is the next round, `v0.3-jdt-ls-bridge`.

## What is in this tag

### Go side (runtime-agent)

- `internal/jdtls/jdtls.go`:
  - State machine now has 5 states on the wire:
    `stopped`, `starting`, `running`, `stopping`, `crashed`.
  - `crashed` is set by a new `watchExit` goroutine when the
    JVM dies without us asking.
  - `Start` and `Stop` accept the `crashed` state as a valid
    source state for recovery.
  - `LastStart()`, `MarkInitialized()`, `JREPath()`,
    `LastError()`, `SetJREPath()` are new public methods used
    by the services layer.
  - `EnsureInstalled` honours two new env vars:
    - `KAIRO_JDTLS_JAR` — path to a pre-staged jar; bypasses
      the download entirely.
    - `KAIRO_JDTLS_URL` — override the download URL.
  - The error envelope is wrapped so the user gets
    "set KAIRO_JDTLS_JAR to use a pre-staged jar, or
    KAIRO_JDTLS_URL to override" when the default URL 404s.

- `internal/api/services.go`:
  - New `JDTLS` interface: `Status`, `Start(payload)`,
    `Stop()`. Documented contract: Start is synchronous w.r.t.
    the user-visible state, never lies about being ready.

- `internal/api/server.go`:
  - New `JDTLS` field on `Services`. Nil-safe (handler
    returns 503-ish error if not configured).
  - New route `/api/v1/jdtls` (GET / POST / DELETE).

- `internal/api/handlers.go`:
  - `handleJDTLS` covers all three methods. GET returns the
    current status; POST takes a payload (jrePath, sourceLevel,
    initializeRootURI, timeoutMs); DELETE returns the
    post-stop status.

- `internal/services/services.go`:
  - `jdtlsService` implements `api.JDTLS` over the underlying
    `jdtls.Manager`. It is the only owner of:
    - the jrePath (mutable, overridden by Start payload)
    - the sourceLevel (defaults to "1.6", per user spec)
    - the initialize handshake (waits for the response,
      tears the JVM down if it fails, refuses to claim
      `initializeOk: true` until the response arrives)
  - Wire-up: `JDTLS: newJDTLSService(cfg.DataDir, cfg.BundledDir, cfg.Logger)`
    in `NewMemoryServices`.

- `internal/api/handlers_test.go` (NEW):
  - 7 unit tests, all pass on this machine.
  - Covers: initial stopped, start without root URI,
    start with root URI, refused re-start while running,
    stop resets state, unsupported method, no-config 500,
    full middleware round-trip with the request id + recovery
    chain.
  - Uses a `fakeJDTLS` so the test does not depend on a real
    JVM, a real download, or a real network.

### TypeScript side (frontend)

- `packages/protocol/src/index.ts`:
  - New `JdtState` (wire state), `JdtStatus` (full status
    payload), `JdtStartRequest` (start payload) types.
  - New `EndpointMap` entries for `GET/POST/DELETE
    /api/v1/jdtls`.

- `packages/java-extension/src/browser/java-service.ts`:
  - The fake `this.setState('ready')` is **gone**. Replaced
    with: set state to `starting` on call, await the agent,
    only flip to `ready` when the agent returns
    `state == "running" && initializeOk == true`. Anything
    short of that is `crashed` with a thrown error so the UI
    cannot pretend the LS is healthy.
  - New local `JavaServiceState` (a superset of the wire
    `JdtState` that adds `uninitialized` and `ready` as
    user-facing local values).
  - `ensureStarted` is idempotent and reuses an in-flight
    promise.
  - `refreshStatus()` is a read-through cache refresher
    (does not change local state, but on network error
    forces `crashed` so the status bar cannot lie about
    being `ready`).
  - `restart()` = `ensureStopped()` + `ensureStarted()`.

- `packages/theia-product/src/main/browser/kairo-status-bar-contribution.ts`:
  - New `kairo.jdtls` status bar entry.
  - Surfaces: local state, agent (wire) state, version, JRE,
    PID, lastError.
  - Polls every 5 s alongside the existing server poll.
  - On Theia `onStart` it pulls the current JDT LS status
    once so a reload / reconnect shows truth immediately.

## What is NOT in this tag

These are explicitly deferred so the skeleton can ship with a
clean, honest boundary:

- **No LSP frame bridge to Monaco.** The agent starts a JVM,
  the JVM can answer `initialize`, but the bytes do not flow
  to the Theia LSP client yet. So no completion, no hover, no
  goto, no outline from the editor. (`v0.3-jdt-ls-bridge`.)
- **No real download yet.** The pinned 1.42.0 jar URL is dead
  (HTTP 404). Two escape hatches exist (`KAIRO_JDTLS_JAR` /
  `KAIRO_JDTLS_URL`) but the default download path still
  fails. (`B-003`, will be addressed in `v0.3-jdt-ls-bridge`.)
- **No crash-restart loop.** A `crashed` state is observed and
  surfaced; there is no automatic restart. Manual Stop +
  Start (or `restart()`) is the recovery path. Auto-restart
  is a follow-up.
- **No JDT LS events on the WebSocket event bus.** The
  agent's `jdtls.Manager.AddListener` hook is not yet wired to
  `api.Services.EventBus`. The UI sees the state by polling
  every 5 s, not by push. Push is a follow-up.

## Manual verification

End-to-end on this machine, agent on port 18097:

```
1) GET /api/v1/jdtls (initial)         → 200  state=stopped  initializeOk=false
2) POST /api/v1/jdtls (no JRE)         → 500  process_spawn_failed (B-003)
3) POST with JDK 21 JRE                → 500  process_spawn_failed (B-003)
4) GET /api/v1/jdtls (after fail)      → 200  state=stopped  jre=<JDK 21>
5) DELETE /api/v1/jdtls                → 200  state=stopped
6) GET /api/v1/jdtls (after stop)      → 200  state=stopped  initializeOk=false
7) PUT /api/v1/jdtls (unsupported)     → 400  invalid_request
```

The 500 in steps 2-3 is the **correct** behavior: the
default download URL is dead, and the agent returns a clean
`process_spawn_failed` envelope instead of pretending. The
state stays `stopped` so the rest of the IDE knows the LS is
not up.

## Why "skeleton" and not "done"

Because the user was explicit: "只有 JDT LS 真正完成初始化
并收到响应，状态才能变为 ready" — and the second half of
that is "并且 LSP frames actually flow to the editor." This
tag delivers the first half (the state machine, the status
bar, the wire protocol) honestly. The second half is the
bridge from the agent's `jdtls.Manager.Receive()` channel to
a Theia `LanguageClient` over a WebSocket, plus the
`MonacoLanguageClient` wiring on the client side. That is a
separate round, larger in scope than the skeleton, and the
right next step.

## Round-3 follow-up (`v0.3-jdt-ls-bridge`)

Pulled from the gap list, in execution order:

1. Fix the JDT LS download URL (or add a tarball unpacker for
   the new `.tar.gz` distribution). One of:
   - point `KAIRO_JDTLS_URL` at a mirror that still ships
     the 1.42.0 jar; or
   - switch `EnsureInstalled` to download the latest
     `jdt-language-server-latest.tar.gz`, unpack, and use the
     jar inside.
2. New WebSocket endpoint `/api/v1/jdtls/lsp` that proxies
   the LSP frame stream between the JDT LS stdio and a
   client-side `MessageReader` / `MessageWriter`.
3. New `KairoJdtlsClient` in `@kairo/java-extension` that
   connects to that WebSocket, implements
   `vscode-jsonrpc`'s `MessageTransport`, and registers a
   Theia `LanguageClient` for `java` files.
4. Wire to `MonacoLanguageClient` so `didOpen` / `didChange`
   / `didClose` actually round-trip with the LS.
5. Replace the polling `refreshJdtStatus` with
   WebSocket-pushed `jdtls.state` events on the existing
   `/api/v1/events` bus.
6. Add an `auto-restart` policy for `crashed` (e.g. 1 retry
   with exponential backoff, then surface to the user).
