# P6 + P7 readiness — what we shipped and what is still blocked

> Tag: not bumping; this is a checkpoint note, not a release.
> Rounds: P6 (Windows real-machine verification) + P7 (Debug)
> Date: 2026-07-18
> Author: Mavis

The user asked for two more rounds (P6 real-machine
verification on a low-spec Windows VM, P7 JDWP debug
end-to-end). Both have one hard external dependency in
common: **the JDT Language Server has to actually start, and
Tomcat 6 has to actually run.** Neither does yet on this
machine, and both are flagged as separate blockers in
`BLOCKERS.md` (B-002 for Tomcat 6, B-003 for JDT LS).
This file documents the honest state and what would
unblock each round.

### What needs to happen to actually close P6

1. **Vendor Tomcat 6.0.53** (or any 6.0.x that survives in
   the user's network). Drop the tarball at
   `bundled/tomcat6/apache-tomcat-6.0.53/`; the agent's
   `tomcat6.FetchCatalinaHomeOrDownload` will pick it up.
   Or set `KAIRO_TOMCAT6_HOME` to a directory the dev
   already has. Either unblocks the server-start path in
   the smoke test.
2. **Vendor or download a JDK 6 toolchain** (or accept
   `--release 6` emulation on JDK 21). The legacy-sample
   `HelloServlet.java` is Java 1.6 source; the build
   refuses without a registered toolchain.
3. **Add a `KAIRO_DATA_DIR` containing a path with a CJK
   segment** to one of the smoke tests. The `Runtime`
   shell I tested with was a non-CJK path; nothing in the
   code is known to break, but a regression test is
   worth its keep.
4. **Run on a low-spec Windows VM** (2 vCPU / 4 GB /
   Windows 10) and capture cold-start, idle RSS, JDT LS
   RSS, and per-action timings. This is a one-time
   measurement pass, not a recurring CI loop. The numbers
   belong in `docs/perf-reports/<date>-windows10-low.md`.
5. **Add a non-admin-user verification** — start the
   dev box as a regular user, run the smoke, confirm
   no elevation is required and `KAIRO_DATA_DIR` is
   writable.

### What is not P6 work

- Anything that depends on the user telling us where
  their JDK 6 lives (B-001). The emulated-v6 fallback
  on JDK 21 is the agreed path.

## P7 — Debug (JDWP attach + Theia Java Debug Adapter)

### What is already in place

The Go agent side is already wired for debug start:

- `internal/api/services.go` `realServerRunner.Debug(id)` —
  stops the running Tomcat and re-starts it with
  `-agentlib:jdwp=transport=dt_socket,server=y,suspend=n,
  address=*:5005` (or any port the user configured).
- `internal/api/handlers.go` `POST /api/v1/servers/{id}/debug`
  is registered; the envelope is `ServerInstance` like
  the normal start, so the UI sees the new port under
  `ports.debug`.
- The Theia side has `@theia/debug` 1.73.1 wired as a
  dependency. We did not bind a `DebugConfigurationProvider`
  for the Tomcat 6 server in this round.

### What needs to happen to actually close P7

1. **Resolve B-003 (JDT LS download URL) first.** The
   debug adapter is on the JDT LS side; without a
   working JDT LS there is nothing to attach to. The
   `v0.3-jdt-ls-bridge` round is the prerequisite.
2. **Register a `DebugConfigurationProvider` for the
   `kairo-java` / `kairo-tomcat` type** so `launch.json`
   entries appear in the VS Code-style debug panel.
3. **Wire the launch config to the agent's
   `DebugConfiguration` shape**: project id, the
   server's debug port, the source paths.
4. **Verify a real Servlet breakpoint hit** end-to-end:
   set a breakpoint on `HelloServlet.doGet`, start the
   server with debug, hit `/kairo/hello?name=Kairo`,
   observe the breakpoint, inspect local vars
   (`request`, `response`), step, continue.
5. **Java 6 minimum-viable**: confirm the same loop
   works against the JDK 6 HotSpot. B-004 covers the
   known JDWP gaps (some reference type info commands
   on Java 6 are not honored by the modern debug
   adapter); the workaround is documented and the
   `kairo.tomcat6` plugin's adapter is the path.

### What is not P7 work

- HotSwap / class reloading. That is `v0.4` at the
  earliest; it requires the same JDT LS bridge and a
  JDWP `RedefineClasses` call from the adapter.

## What the user should know

The agent's `/api/v1/servers/{id}/debug` endpoint already
returns a real `ServerInstance` envelope with the new
debug port. Anyone with a real Tomcat 6 + JDK 6 (or the
emulated-v6 fallback on JDK 21) can call it from
`curl` or from a stub UI and observe the JDWP listen
socket. The Theia-side debug UX is the missing piece;
it does not block the runtime path, only the editor-side
breakpoint view.

## Combined P6/P7 next step

If the user can:
- drop `apache-tomcat-6.0.53.tar.gz` into
  `bundled/tomcat6/` and run `scripts/fetch-tomcat6.sh`'s
  unpack (or set `KAIRO_TOMCAT6_HOME` to a directory
  that already has it), and
- pre-stage a JDT LS 1.42.0 jar (or a working mirror of
  it) at `bundled/jdtls/` (or set `KAIRO_JDTLS_JAR`),

then this round (P6+P7) becomes executable on a real
Windows box within a working day. Until then, the
honest status is "all the wire plumbing is in; the
external artifacts are not, and the user-visible UI
parts that depend on a running JDT LS / Tomcat 6 are
unverified."
