## 缺陷台账

### BUG-20260826-201 (P1) — Project Structure 对话框加载时编码显示错误（始终 UTF-8）

**现象**: TC-PROJ-013 中 solo-proj 的 `File encoding` 期望 gbk 实际为 utf-8。

**根因**: `packages/project-extension/src/browser/project-structure-dialog.tsx:173` 仅处理 `ProjectConfig` 形态 `encoding.default`，但 `GET /api/v1/projects` 实际返回 `domain.Project` 形态（`encoding: "gbk"` 字符串，`sourceLevel` 等顶层字段）。`config.encoding?.default` 为 undefined，遂回退默认 utf-8；同理 `sourceLevel` 等也未能正确回填。

**修法**: 前端兼容双形态：`packages/project-extension/src/browser/project-structure-dialog.tsx:158-197` 增加对 `raw.encoding` 字符串与 `raw.Encoding`、以及 `raw.sourceLevel`/`raw.targetLevel`/`raw.toolchainId` 与 `sourceRoots`/`sourceLayout` 双路径的探测与归一化；对 JDT 返回的绝对 sourceRoots 做相对化（见 BUG-203）。

**验证**: 重建 `@kairo/project-extension` + `apps/browser` 后 Lane B 重启，TC-PROJ-013/019 回归通过。

### BUG-20260826-202 (P0) — PUT /api/v1/projects/{id} 无法处理前端 ProjectConfig 形态（encoding 对象）

**现象**: TC-PROJ-015/019/020 的保存均失败，响应 `json: cannot unmarshal object into Go struct field Project.encoding of type string`，对话框内 `kairo-ps-error` 误报，Toaster 显示 Failed to save。

**根因**: `runtime-agent/internal/api/handlers.go:232` 的 PUT 分支仅 `json.Unmarshal` 到 `domain.Project`（`Encoding string`），而前端 `Project Structure` 保存按 `protocol.ProjectConfig` 发送 `encoding: {default:"gbk"}` 对象，导致解码失败。协议与实现不一致：协议定义为对象，测试与存储层为字符串。

**修法**: 双端兼容：前端 `project-structure-dialog.tsx:615` 在 PUT 前同时写入 domain 兼容字段（`encoding` 字符串、`sourceRoots`、`sourceLevel` 等顶层）；后端 `handlers.go:233` 增加对 `encoding` 对象形态的探测与修复（提取 `default` 字段后重试解码），确保两种形态均可接受。

**验证**: 重建 `runtime-agent/bin/kairo-runtime` + 前端后，PUT 成功，TC-PROJ-015/019/020 通过。

### BUG-20260826-203 (P1) — JDT 合并的 sourceRoots 绝对路径导致保存校验失败

**现象**: 保存时 `save .kairo/project.yaml: validate: invalid path "/private/tmp/kairo-w1b/solo-proj/src": path is absolute`。

**根因**: `project-structure-dialog.tsx:219` 直接将 `POST /api/v1/jdtls/project` 返回的 `sourceRoots`（绝对路径 `/private/tmp/.../src`）合并进 `sourceDirs`，保存时原样作为 `sourceRoots`/`sourceLayout.src` 提交，触发 `pathpolicy.ValidateRelativeConfigPath`（`strings.HasPrefix(value,"/") → ErrAbsolutePath`）。

**修法**: 同文件合并前相对化：`if (src.startsWith(wsCtx.root)) rel = src.slice(wsCtx.root.length).replace(/^\/+/, "")`，并对 `lib` 展开等后续保存路径做相对化校验。

**验证**: 重建前端后，TC-PROJ-015 的 PUT 不再报绝对路径，7.5m 回归通过。

### BUG-20260826-204 (P2) — 测试基建 `purgeCatalog` 与 `agentJson` 在 workspace-scoped 模型下失效

**现象**: 多处测试的 `GET /projects` 不带 `X-Kairo-Workspace-Id` 时返回 `[]`，导致 `purgeCatalog` 未删除任何项目，跨用例污染（如 solo-proj 被前序改为 utf-8 后影响后续 gbk 断言；TC-PROJ-001 的计数与 workspace 隔离不匹配）。

**根因**: `runtime-agent/internal/api/api_handler.go:158` 的 `HandleProjects` 已改为 `List(wsID)` workspace-scoped，但测试 helpers 仍用全局 GET。

**修法**: `tests/e2e/comprehensive/helpers-ch810.ts:215` 重写 `purgeCatalog`：先 `GET /workspaces`，再对每工作区带 header `X-Kairo-Workspace-Id` 拉取并删除项目；`ch10-project.spec.ts:37,256` 的 `ensureFixtures` 与 `TC-PROJ-007` 改为 workspace-scoped 校验与 `fs.realpathSync` 路径归一；`TC-PROJ-001` 改为打开 `multiDir` 并断言 `2 projects` 的 workspace-scoped 计数。

**验证**: 隔离与全量回归均稳定通过。
