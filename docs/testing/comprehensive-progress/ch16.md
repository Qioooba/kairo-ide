## 缺陷台账

### BUG-20260828-600 (P2) — JSON/XML/WebXml 补全因占位 range 导致建议永不显示

**现象**: TC-JSON-002/003 在 `package.json` 内 `"` 后 `Ctrl+Space` 时 suggest-widget 显示 `No suggestions.`（count 0，`aria-setsize` 不含预期 15/5/9），即使 `buildCommonJsonSchemas` 已返回 15 项；同理 TC-XML-002/003/004 的 web.xml/TLD 元素与属性补全亦为 0（count 0）。

**根因**: `packages/jsp-extension/src/browser/json-language.ts:103,119` 的 `createCompletion/createSnippetCompletion` 硬编码 `range: {1,1,1,1}`；`xml-dtd-completion.ts:25` 的 `item()` 与 `webxml-completion.ts:32,51` 同理。Monaco 的 `provideCompletionItems` 若返回的 `range` 不包含光标位置，编辑器会过滤该建议（置信区间外），导致建议列表为空。`properties-language.ts` 已正确使用 `model.getWordUntilPosition` 的 `word` range，故 properties 正常。

**修法**:
- `json-language.ts:85-120` 改为接受可选 `range`，`provideCompletionItems` 内 `const word = model.getWordUntilPosition(position); const range = new monaco.Range(...); const withRange = items=>items.map(it=>({...it, range}))` 统一注入；
- `xml-dtd-completion.ts:18-27,121-158` 同理移除占位 `range`，`provideCompletionItems` 计算 `word` range 并 `withRange`；
- `webxml-completion.ts:31-51,110-138` 同理，`buildUrlPatterns(range)` 与 `ci` 移除占位，`provideCompletionItems` 计算 `word` range 后注入。

**验证**: `pnpm --filter @kairo/jsp-extension build && cd apps/browser && pnpm build` 后重启 lane E，`probe-json-suggest` 显示 `count 12, aria-setsize 15, labels 含 author/dependencies`，`probe-xml-suggest` 显示 `count 12, labels 含 context-param/filter` 与 `count 12, labels 含 attribute/taglib`；回归 `ch16` 8/8、`ch15` 12/12 通过。

### BUG-20260828-601 (P2) — XML 属性补全分支永不可达（`isInsideOpenTag` 重叠）

**现象**: TC-XML-004 在 `<web-app `（尾空格）后 `Ctrl+Space` 期望出现 `xmlns/xmlns:xsi/xsi:schemaLocation/version/encoding/id` 6 项，但实际返回 web.xml 元素列表（`context-param/filter` 等 12 项），与预期不符。

**根因**: `xml-dtd-completion.ts:134-155` 先 `if (isInsideOpenTag(lineBeforeCursor))` 返回元素建议，`IsInsideOpenTag` 为 `lastOpen > lastClose`，对 `<web-app ` 与 `<` 均成立，故元素分支恒先命中；后置的 `lastTagStart` 属性分支虽等价但永不可达。测试仅因放宽断言（允许 `filter`）而误通过。

**修法**: `xml-dtd-completion.ts:134-148` 改为在 `isInsideOpenTag` 内先判断 `afterLt = lineBeforeCursor.substring(lastOpen+1); if (/\s/.test(afterLt)) return withRange(buildCommonAttributes())`，再走元素分支；移除重复的后置属性分支。

**验证**: 重建后 `probe-xml-suggest` 对 `<web-app ` 的 `Ctrl+Space` 返回 6 项 `xmlns/xmlns:xsi/xsi:schemaLocation/version/encoding/id`，TC-XML-004 回归通过（`labels 含 xmlns`）。

### BUG-20260828-602 (观察) — Properties 保存未做 ISO-8859-1 `\uXXXX` 转义（P1）

**现象**: TC-PROP-004 写入 `testKey=你好` 后 `fs.read` 得到 `greeting=hello\n\ntestKey=���`（3 个 replacement），而非 `testKey=\u4f60\u597d`；虽未写 `?` 但为 UTF-8 裸字节在 GBK 环境下的乱码，未满足“ISO-8859-1 + `\uXXXX` 由 agent 处理；BMP 外字符输出代理对”。

**根因**: 前端保存直接走 Theia FileService 的 UTF-8 写入，未经 `Safe Encoding Service` 的 `encode` 回绕校验与 `\uXXXX` 转义；`properties` 的编码路径在 Go agent 侧未对 `.properties` 强制 `iso-8859-1` + 转义（与 `workspace-encoding` 的 `properties` 特殊分支缺失）。

**状态**: 已记录，未在本轮修复（不阻断 16 章通过，计数为“部分通过”）；建议后续在 `runtime-agent/internal/encoding` 增加 `isPropertiesFile` 分支的 `\uXXXX` 编码器（BMP 外输出代理对）。
